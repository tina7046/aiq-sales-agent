{# Pipeline Snapshot — structured agent output ===================================================================== Renders the Pipeline Snapshot workflow's per-run output as an in-feed agent response, following the "open document" treatment the `agentMessage` macro already uses (no chat bubble around long-form content — the response IS the document). Consumed by `_home_conversation_messages.html → agentMessage(msg)` when the message carries a `snapshot` block. Rendered inline INSIDE the agent article, so the article's `data-sh-conv-msg` value is what the workflow side panel's Activity list anchors to (see `findMessage` in home_conversation.js — it resolves a run's `messageId` against that attribute, not a DOM id). Data contract — `snapshot` object, per run: { dateLabel: String, // "August 11, 2026" date: ISO String, // machine-readable titleLabel: String, // "Pipeline Snapshot" freshness?: { text, source }, summary: String, // 1–2 sentence outcome-oriented lead metrics: { heading: String, // "Pipeline at a glance" items: [ { id, label, value, tone?: 'positive' | 'warning', // colours the value delta?: { text, direction } // "up" | "down-good" | "up-warning" } ] }, changes: { heading: String, // "What changed" ariaLabel: String, columns: [ { id, label } ], rows: [ { id, opportunityId, …one field per column id } ] }, attention: { heading: String, // "Needs your attention" items: [ { id, severity, severityLabel, // 'high' | 'warning' | 'info' title, subtitle, detail, recommendation?, opportunityId } ] }, actions: { heading: String, // "Recommended actions" items: [ { id, label, kind, // 'outreach' | 'task' | 'research' description?: String, primary?: Boolean, opportunityId?: String } ] } } Every block below `header` is optional — a snapshot with only a summary renders as a summary, so a run that produced less than a full analysis doesn't need a different message type.
