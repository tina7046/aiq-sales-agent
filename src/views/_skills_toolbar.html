{# Seller Home — Skills toolbar (tab chips + filter button + live region) ===================================================================== Lifted verbatim out of `skills.html` on 2026-08-17, when the Skills landing gained a second design version (`/skills-v2.html`; see `_skills_body_v1.html` for the split's rationale). Both version bodies include THIS file, so the tab contract exists exactly once: one SSR count loop, one radiogroup ARIA pattern, one roving-tabindex rule, one filter-button dispatch. Version B is expected to RESTYLE this toolbar, not re-author it — rules scoped to `.seller-home--skills-v2` in skills.scss can repaint every element below without a second copy of the markup. Only reach for a variant branch inside this file if a version needs different STRUCTURE (an extra control, a different element order); anything purely visual belongs in CSS, or the versions start drifting on counts and keyboard behavior — which is what this extraction exists to prevent. Context expected from the includer (Nunjucks includes can read the including template's variables, so each version body binds these from `skillsData` before including): tabs — `{ items[], defaultTabId }` from skills.json. skills — the catalog array; counted per tab below. filterAction — `{ label, icon }` for the trailing icon button. DOM contract consumed by `bindSkills()` in skills.js — every hook below is load-bearing, so keep the attribute names when restyling: `data-sh-skills-toolbar`, `-tabs`, `-tab`, `-tab-ownerships`, `-tab-count`, `-filter`, `-status`. #} {# ── Skills toolbar (tabs + filter button) ───────────────────────── Structural clone of Scheduled's toolbar, namespaced separately (`.seller-home__skills-*`) so a Scheduled-only tweak can't accidentally regress Skills and vice versa (duplicate-not-shared strategy, confirmed decision 2026-07-31). ARIA note: these are filter chips over one list, NOT SLDS tabpanel-swapping tabs. So we use `role="radiogroup"` + `role="radio"` per the WAI-ARIA authoring practices for "pick one option that changes what's shown" — `role="tab"` implies a `role="tabpanel"` sibling per option, which this design doesn't have (the list stays in place; only row visibility flips). Counts are rendered server-side by iterating `skills` per tab: Nunjucks's outer-scope `{% set %}` DOES propagate through this build (probed on the Scheduled build 2026-07-30), so first-paint counts are always in sync with the JSON without a JS hydration step. `bindSkills()` also recomputes counts client-side so any future JS-driven skill add/remove keeps them correct. `defaultTabId` from skills.json controls the first-paint active chip (server-side). URL hash drives the runtime active tab; `bindSkills()` reads `location.hash` on load and updates the highlight + row filter to match. #}
